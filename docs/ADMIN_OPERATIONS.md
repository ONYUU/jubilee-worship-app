# 쥬빌리워십 관리자 운영 안내

## 1. 접근 원칙

1. 공개 회원가입은 제공하지 않습니다.
2. Supabase Auth 사용자라고 해서 자동으로 관리자가 되지 않습니다.
3. `admin_users`에 `is_active=true`로 등록된 `owner` 또는 `editor`만 `/admin`을 사용할 수 있습니다.
4. 활성 `owner`만 `/admin/admins`에서 이메일 초대·재발송·비활성화·역할 변경을 수행합니다. 신규 승인 계정은 항상 `editor`로 시작합니다.
5. 이메일·비밀번호 인증 공급자는 기존 관리자 로그인을 위해 활성화하고, 공개 신규 가입은 Auth 전역 설정에서 차단합니다.

## 2. 일정 관리

- 실제로 확정된 일정만 등록합니다. “매월 첫 번째 금요일” 규칙으로 미래 일정을 자동 생성하지 않습니다.
- 일정이 취소되면 삭제보다 `cancelled` 상태를 사용해 방문자에게 변경 사실을 알립니다.
- 연기된 일정은 변경된 시작 시간을 입력하고 `postponed` 상태 및 관련 공지를 함께 게시합니다.
- 입력 시각은 관리자 화면에서 Asia/Seoul 기준으로 표시되고 DB에는 `timestamptz`로 저장됩니다.
- 2026년 9월 4일 초기 일정은 공식 공개 직전에 인스타그램 최신 공지와 다시 대조합니다.

## 3. 공지 관리

- 유형: 일반, 중요, 일정 변경, 취소
- `starts_at` 이전에는 공개 view와 RLS 모두에서 보이지 않습니다.
- `expires_at`이 지나면 공개 view와 RLS 모두에서 자동 제외됩니다.
- 상단 고정 공지는 방문자가 닫을 수 있으며 닫은 상태는 공지 ID별로 브라우저에 저장됩니다.

## 4. 미디어 관리

- 현재 운영 채널: `@JUBILEEWORSHIP-25`
- 허용 channel ID: `UCxmosyyztNo7HBUOdN_gy9w`
- URL 형식: `watch`, `youtu.be`, `live`, `shorts`
- 키워드 검색 결과나 동명 해외 채널 영상을 등록하지 않습니다.
- 새 URL은 video ID를 추출해 표준 `watch` URL로 저장합니다.
- 앱과 DB에 명시적으로 승인된 video ID만 공개할 수 있습니다. 승인 목록에 없는 영상의 공개 요청은 초안으로 저장됩니다.
- 새 공식 영상을 승인하려면 운영 채널 게시물임을 사람이 확인한 뒤 앱의 `APPROVED_YOUTUBE_VIDEO_IDS`와 DB 비공개 allowlist를 같은 배포에서 함께 갱신합니다.
- `youtube_channel_id`와 `verification_status`는 관리자 입력값을 신뢰하지 않고 DB 트리거가 설정합니다.
- 재생 불가·비공개 영상은 삭제 전에 대체 URL을 확인합니다.

## 5. 이미지 업로드

- 허용 형식: JPEG, PNG, WebP, AVIF
- 최대 크기: 10MB
- SVG: 일반 관리자 업로드 금지
- 파일명: 브라우저가 난수 기반 object key를 생성하며 원래 파일명을 공개 URL에 사용하지 않습니다.
- 업로드 전에 출처, 사용 권한, 인물 공개 동의 여부, 대체 텍스트를 확인합니다.
- 업로드가 완료됐지만 콘텐츠 저장이 실패한 고아 객체는 Storage 목록에서 확인 후 API로 삭제합니다.

## 6. 섬기는 이

- 초기 공개 범위는 공식 페이지에 공개된 김두진 목사, 최희락 목사, 조예희 전도사입니다.
- 팀원 개인 사진·약력은 당사자 및 교회 내부 기준에 따른 동의 확인 후 추가합니다.
- 청소년 팀원은 명시적 동의 없이 개인 프로필을 만들지 않습니다.

## 7. 앱 법적 문서

- 표시 운영주체는 `쥬빌리 워십`, 문의·개인정보 이메일은 `sundoojubileeworship@gmail.com`입니다.
- `editor`는 개인정보처리방침·이용약관 초안만 작성·수정·삭제합니다.
- 기본 템플릿의 `[[오너 확인 필요]]` 항목은 실제 운영 리전·보유 기간·외부 처리 계약을 확인한 내용으로 교체합니다. 마커가 남아 있으면 오너 공개가 차단됩니다.
- 앱 개인정보처리방침에서 설치 식별자·푸시 토큰·알림 선택·보유·비활성화 처리가 누락되면 공개 액션이 차단됩니다.
- 예배 알림 선택은 종교적 관심을 추론할 수 있으므로 이름·이메일·광고 식별자와 결합하지 않고 광고·추적·프로파일링에 사용하지 않는다는 설명을 포함합니다.
- 개인정보처리방침의 비활성 정보·발송 기록 보유 기간, 삭제 주기, 수탁자·국외 처리 6개 항목은 템플릿의 정확한 항목명 뒤에 실제 값을 입력해야 합니다. `확인 필요`, `미정`, `추후`, 단순 `최종 확정` 치환은 공개 검증을 통과하지 못합니다.
- 약관도 준거법·관할·면책 범위·미성년자 이용 안내의 실제 값을 모두 입력해야 합니다.
- 확정 기준은 알림 해제·무효 토큰 원문 최대 24시간, 180일 미활동 설치 비활성화, 비활성화 후 30일이 경과한 설치 정보와 90일이 경과한 발송 상세기록을 다음 일일 자동 정리에서 삭제하는 것입니다. 작업 지연·적체 시 실제 삭제는 다음 정상 실행 이후 완료될 수 있습니다.
- 이 기준의 cleanup RPC·cron·삭제 회귀 테스트와 원격 적용은 완료했고 원격 cron 성공 이력 4회를 확인했습니다. 실제 만료정보 삭제를 확인하기 전에는 앱 정책을 공개하거나 `/privacy`를 스토어 개인정보 URL로 사용하지 않습니다.
- `owner`는 본문·버전·효력일과 확정 운영주체·이메일 포함 여부를 검토한 뒤 공개합니다. 공개하면 같은 종류의 이전 공개본은 원자적으로 철회됩니다.
- 공개 `/privacy`는 owner가 공개한 최신 앱 개인정보처리방침을 표시합니다. 유효한 공개본이 없으면 `앱 개인정보처리방침 공개 전`으로 표시되며, 이 상태로는 스토어에 개인정보 URL을 제출하지 않습니다.

## 8. 예배 알림 승인·예약

1. `owner`가 공개된 `scheduled|postponed` 예배를 선택합니다.
2. `전날 19:30` 알림과 `당일 1시간 전` 알림의 제목·본문을 각각 확인합니다.
3. `두 알림 승인·예약`을 실행하면 두 캠페인이 같은 예배 시각 스냅샷을 기준으로 owner 승인 상태로 저장됩니다.
4. 예배 시각·공개 상태·승인 문구 기준이 바뀐 예약은 `재승인 필요`로 표시됩니다. 기존 예약이 자동 이동하는 것으로 간주하지 말고 두 문구를 다시 승인합니다.
5. 승인·예약은 발송 완료가 아닙니다. 운영 scheduler가 `scheduled_for`부터 15분 안에 queue하고, `dispatch-notifications` worker와 외부 발송 설정이 활성화되어야 실제 기기로 발송됩니다. 15분을 넘긴 예약은 늦게 발송하지 않고 만료 처리합니다.

## 9. 시험 기기 푸시 확인

1. 알림을 허용하고 서버 등록을 마친 `development`·`preview` 실기기의 알림 설정에서 `연결 코드 만들기`를 누릅니다. `production` 앱에는 이 기능이 표시되지 않습니다.
2. 앱에 표시된 12자리 코드를 10분 안에 활성 `owner`가 `/admin/notifications`에 직접 입력합니다. 코드는 1회용이며 새 코드 발급·승인 또는 만료 감지 시 서버의 HMAC digest도 제거됩니다. 미사용 만료 코드는 5분 cleanup 주기 안에 제거됩니다.
3. 공개 설치 등록만으로 시험 대상이 되지 않습니다. 오너가 코드를 승인한 active endpoint만 마스킹된 목록에 표시됩니다.
4. 화면에는 환경·플랫폼·앱 버전·endpoint 끝 6자리만 표시합니다. 설치 UUID, 설치 secret, Expo token, token hash, 코드 digest를 표시·로그 기록하지 않습니다.
5. 승인 목록에서 대상 1대와 제목·본문·딥링크를 확인한 뒤 `시험 캠페인 큐 등록`을 실행합니다. Server Action, Edge Function, DB RPC가 owner·승인 상태·활성 상태·비운영 variant를 다시 검증합니다.
6. 같은 화면 요청은 숨은 request UUID로 멱등 처리됩니다. 동일 UUID의 내용이 달라지면 실패하고, 동일하면 기존 캠페인만 반환합니다.
7. 필요하면 `승인 해제`를 누릅니다. 아직 pending인 시험 큐는 취소되지만 worker가 이미 `processing`으로 claim한 작업은 회수할 수 없습니다.
8. 큐 등록은 실기기 도착을 의미하지 않습니다. 실제 수신 확인은 별도로 `dispatch-notifications`, FCM/APNs 자격 증명, 앱 알림 권한을 준비한 뒤 수행합니다.

## 10. 관리자 비활성화

1. 오너가 `/admin/admins`에서 대상 계정을 비활성화합니다. 서버는 DB `is_active=false`를 먼저 적용합니다.
2. DB 권한은 기존 JWT가 남아 있어도 즉시 차단됩니다. 이후 서버 전용 Auth Admin API가 해당 Auth 계정을 장기 ban합니다.
3. Auth ban이 일시 실패해도 DB 접근 차단은 유지됩니다. 관리자 화면의 재시도 안내를 따라 Auth ban을 완료합니다.
4. 자기 자신 비활성화, 마지막 활성 owner 비활성화·강등은 DB와 화면 모두에서 차단됩니다.
5. 일반 authenticated 사용자와 비활성 관리자의 직접 Data API 읽기·쓰기 시도가 거부되는지 확인합니다.

## 11. 장애 시 확인 순서

1. `/admin`에 “설정 필요”가 표시되면 Supabase URL과 publishable key를 확인합니다.
2. 로그인 후 권한 없음이면 Auth UUID와 `admin_users.user_id`, `is_active`를 확인합니다.
3. 저장 실패 시 필수 입력, YouTube 승인 video ID, 이미지 path 형식을 확인합니다.
4. 공개 반영이 지연되면 저장 성공 여부와 Next.js revalidation 경로를 확인합니다.
5. 오류 원문·토큰·환경 변수 값은 외부에 전달하지 않습니다.
